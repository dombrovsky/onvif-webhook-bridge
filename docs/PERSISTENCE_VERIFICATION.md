# Phase 5 persistence verification and handoff

Date: 2026-10-15. Generic phase 5 implementation and required automated gates are complete. Tests used temporary databases, deliberately synthetic credentials, actual disposable onvifsim and a local HTTP recorder. No real camera or action destination was contacted. Real-device activation/reset mappings and reboot/network recovery remain **pending**; HTTP 2xx proves transport acceptance only.

## Delivered scope

`Persistence/ConfigurationStore.cs` coordinates complete configuration snapshots with direct parameterized SQL, immediate write transactions, optimistic revision conflicts and commit-before-apply ordering. The existing `CameraPipeline`, `CameraSupervisor`, independent subscription workers, dispatcher, phase 2 components and shared WS-Addressing adapter are reused. No polling, lease, cleanup-before-replacement, recovery cleanup retry, failure-isolation or inspector-admission behavior was changed. `HttpAction` now compares validated values so an equivalent save does not invalidate unrelated rule revisions/queued jobs or reset matching state.

Two embedded, versioned transactional SQL migrations create configuration revision, cameras and administrator (version 1), then named rules and ordered action headers (version 2). Foreign keys protect referenced cameras and cascade deleted rules' headers. Configuration includes enabled state, exact topic/condition/boolean/transition/cooldown settings, action method/retries, recoverable camera credentials and full action URL/headers/body. Event history, transition identities, cooldowns, queues, execution/camera status and responses remain transient; no tables exist for them.

`ConfigurationEdits.cs` supplies explicit preserve/replace/clear operations and masked read views. Camera username/password and action URL/headers/body are represented by presence flags on reads. Required fields cannot be cleared to create invalid configurations. Complete detached snapshots are validated before SQL changes or active snapshot changes. `BootstrapAdministrator` inserts only if absent, storing a salted PBKDF2-HMAC-SHA256 hash (600,000 iterations, 16-byte random salt, 32-byte result). It does not expose the hash or provide login/setup/reset routes. Environment/password-file bootstrap and authentication belong to phase 6.

`AddPersistentCameraPipeline` registers restoration before dispatcher/supervisor startup. Program uses it with `ONVIF_DATA_DIRECTORY` (Linux default `/data`); a new database starts empty and existing enabled configuration restores/reconciles. The old in-memory registration remains available for existing tests/in-process hosts. `/health` is still the only HTTP route. This phase adds no administration/authentication API, UI, Compose, workflow, TaskFlow, production deployment or image publication. The diagnostic probe and renewal adapter sources were not changed.

`StorageFiles.cs` creates/restricts Linux storage to the effective UID and 0700/0600. Linux `statx` verifies ownership/type of the directory, database and existing sidecars; final-path symlinks and foreign owners fail closed. Deliberately missing owner access is rejected rather than repaired into writable access. SQLite creates sidecars within the private directory from the 0600 database. SQL/filesystem exceptions are reduced to fixed safe categories without provider messages or inner exceptions. Startup checks integrity/schema/references/configuration; failures never trigger deletion/reset of data. [DATA_STORAGE.md](DATA_STORAGE.md) documents the complete contract, trust boundaries, Windows ACL limitation and sensitive backup/restore procedure. These restrictions are **not encryption at rest**.

Windows filesystem testing is not counted as Linux permission evidence.

Storage tests run against temporary on-disk databases, not an in-memory SQLite substitute. The shared JIT/native `StoragePath` covers full rule/action/camera round-trip (including apostrophes in IDs), secret preserve/replace/clear and invalid operations, matching validation, oversized configuration, initial/earlier/future schemas, rollback of a partially attempted migration, SQL trigger-injected save rollback, foreign-key rejection, stale revisions, unchanged active snapshot on failure, equal-value queued-job eligibility and committed-edit invalidation. It verifies the hash format against PBKDF2, rejects silent bootstrap replacement, and proves consistent SQLite online backup/restore. Seeded fake secrets in provider-error/corrupt-file paths never escape exceptions; corrupt bytes and future schema versions remain intact. Fresh runtime objects have empty history/status/queues. Separate xUnit cases exercise simultaneous independent store writers (one succeeds, one conflicts) and host startup rejection of corrupt bytes before any active configuration.

The shared `PersistencePath` loads an actual onvifsim scenario via `/api/scenario`. It seeds configuration with workers stopped, then starts two entirely fresh DI hosts from that same database. Each startup restores an enabled authenticated camera, a disabled camera, occurrence/transition rules and secret POST URL/header/body configuration. Events come only from `/api/cameras/synthetic-camera/events`. A local Kestrel recorder verifies restored delivery. First true after each restart creates no transition action, occurrence cooldown starts empty, false remains in history, and the next true produces the transition action while the occurrence rule remains in cooldown. No event/status/job is restored. A trigger-injected failed disable preserves the same active camera snapshot; a committed disable joins cleanup and changes supervisor status, then committed enable resubscribes. The existing phase 4 scenario separately retains independent-camera failure isolation, cleanup retry, leases and bounded shutdown. Both scenarios execute under JIT and Linux NativeAOT.

Development failures are not passes: initial compiler/analyzer errors for the platform guard on `UnixCreateMode` and the xUnit single-item assertion were corrected without suppression. One restricted storage test invocation could not connect to its test host within 90 seconds; the same storage checks passed with the necessary execution permissions, and the final full suite passed.
