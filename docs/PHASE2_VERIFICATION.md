## Event preservation and bounds

- Matching uses the exact displayed `Topic` string: concatenated text of the library's topic nodes, with prefixes, case and whitespace preserved. No alias rewriting or prefix stripping is performed. Dialect, exposed topic attributes (including namespace declarations when supplied), serialized topic nodes and original message XML are retained.
- The schema Message supplies the original camera timestamp text, an optional XML timestamp parse, and the property-operation text. Missing/invalid optional content yields fixed diagnostic categories; unknown operations remain ordinary observations. Receipt time is supplied separately. Vendor elements that merely resemble ONVIF schema elements cannot satisfy scalar conditions.
- Source, Data and Key are ordered collections, preserving duplicate names, absent versus empty values, SimpleItems, ElementItems and unknown child elements. Each field retains its XML; the complete exposed message contains additional containers, attributes and extensions. Snapshot strings and read-only collections do not retain references to the mutable source tree.
- Retained variable content is bounded to 64 KiB of UTF-8 payload per event, with a 16 KiB cap per string/XML preview, 256 total section items, up to 256 topic nodes and up to 256 topic attributes. Strings truncate at Unicode scalar boundaries. XML uses a capped writer instead of allocating an unbounded `OuterXml` copy. Fixed diagnostic labels and managed-object overhead are additional, bounded by these count limits. Library DOM allocation and incoming SOAP transport-size limits are not enforced by these post-parse components; transport hardening belongs to worker work.
- Raw XML is complete when it fits both the per-preview and shared event budgets. Truncated XML previews may be incomplete XML. `Truncated` and `ContentTruncated` make this explicit. Clipped content cannot safely establish exact equality or identity: it remains in history but produces no admissions and clears affected camera transition baselines. The next complete observation establishes an unknown baseline. This conservative handling prevents clipped text from accidentally matching a configured value.
- History retains at most 100 notifications globally and 1 MiB of variable payload, evicting the oldest until both limits hold. Byte pressure can leave fewer than 100 entries. Every Process call adds the notification before evaluating rules or invoking admission, including false, unmatched, Initialized, Deleted, disabled and truncated events. There is no deduplication.

**Library loss versus application limits:** 0.11.2 exposes a parsed message subtree, not original SOAP wire bytes/full envelope. Endpoint-reference details are not a part of the normalized matching model; the existing convenience-method reference-parameter limitation remains. Namespace information not exposed by the library cannot be reconstructed. Application truncation is separately flagged and does not claim to recover this library loss. XML snapshots are serialized DOM content, not byte-for-byte wire captures; complete available raw content is retained within the documented bounds.

## Matching, transition and admission contract

Rules start disabled. Camera/topic, section/name and text values are ordinal and case-sensitive. Only named scalar SimpleItems satisfy conditions; duplicate scalar fields match if any present value matches. Source and Data are explicit. Boolean mode accepts only XML lexical `true`/`1` and `false`/`0`; text mode preserves exact values. Multiple independent rules are evaluated for every notification.

Transition rules require a field condition. First/Initialized observations establish a baseline, Deleted clears the relevant identity, and only known nonmatching-to-matching changes become eligible. Nonmatching observations update baselines during cooldown. Unknown operations use ordinary transition evaluation. Rule edits/removal/enable changes reset state and cooldown; setting an unchanged rule retains them. `ResetCamera` resets that camera's transition state for a new subscription epoch, preserving per-rule cooldown. Restart creates empty state. Future workers must call ResetCamera when subscription epochs change.

Transition identities are partitioned by immutable rule (and therefore camera/topic) and the complete Source/Key collections. Length-framed ordinal sorting preserves multiplicity while ignoring collection order. The selected scalar Source condition field is excluded. Names, missing/empty values, additional attributes and structured XML participate. Extra attributes are sorted by expanded name; structured content uses the retained XML representation, with no semantic XML/prefix rewriting. Without Source/Key fields the rule's camera/topic partition is the identity. The cache holds at most 1024 identities globally across at most 256 configured rules, with deterministic FIFO eviction (reads do not refresh order). Eviction restores unknown-baseline semantics. Rules limit each configured string to 4096 UTF-16 code units; identity strings are bounded by the normalized event payload and framing/count limits.

One lock protects rule snapshots, transition updates, cooldown checks and admission callbacks. The `TimeProvider` seam uses monotonic timestamps; tests never sleep to advance cooldown. A bounded synchronous callback returns whether a test recorder/future queue accepted the decision. Cooldown starts only on acceptance, is per rule across identities, and applies at the exact elapsed-time boundary. Rejection or callback failure consumes no cooldown and cannot block another rule's decision. Transition state still updates before admission: rejected/suppressed transitions and repeats are never replayed later. A later delivery failure would retain already-consumed cooldown; delivery is not implemented here.

The callback must not block or reenter configuration/processing. Phase 3 must attach bounded queue admission and later recheck camera/rule eligibility/revisions before execution. These components intentionally introduce no speculative dispatcher/configuration framework.
