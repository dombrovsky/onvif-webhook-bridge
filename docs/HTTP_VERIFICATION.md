# Phase 3 HTTP verification and handoff

Historical phase 3 record. Phase 4 renames SingleCameraPipeline/AddSingleCameraPipeline to CameraPipeline/AddCameraPipeline and replaces SingleCameraWorker with supervised per-camera workers. Current use, evidence and hardware gates are in [the lifecycle handoff](LIFECYCLE_VERIFICATION.md).

Date: 2026-10-15. Generic single-camera HTTP forwarding is complete. Verification used only onvifsim, synthetic credentials and an ephemeral local HTTP recorder. No physical device, real destination or live transition action was used. A 2xx result means HTTP transport acceptance; destination-side effects are unverified. Real-device activation/reset mapping checks remain **pending**.

## Delivered scope and use

`Dispatch/HttpAction.cs` validates detached action snapshots; `DispatchQueue.cs` provides bounded admission and round-robin scheduling; `HttpActionDispatcher.cs` executes HTTP through HttpClientFactory; `ExecutionStatus.cs` carries safe results. `SingleCameraPipeline.cs` owns in-memory camera/action-rule snapshots, revisions, matching/admission, manual tests and status. `PipelineServices.cs` registers the existing history, normalizer and RuleState plus the dispatcher and one `Onvif/SingleCameraWorker.cs` hosted service. Program registers these services and still exposes only health. The diagnostic console and shared WS-Addressing adapter remain unchanged.

There is deliberately no public configuration loader, administration API, manual-test route, authentication implementation, UI or persistence in this phase. The default executable has no configured camera/rules and initiates no forwarding. For an authorized in-process host/test, call `AddSingleCameraPipeline()`, build its service provider, then call `SingleCameraPipeline.Configure(camera, actionRules)` before starting hosted services. `ActionRule` joins a phase 2 `ForwardingRule` to a validated `HttpAction`; matching rules start disabled by default. The shared integration scenario is an executable example using synthetic configuration only. Real configuration must remain private and ignored.

`Process` retains inspector history before matching/cooldown/admission, including false/unmatched and disabled-camera observations. The worker passes its camera snapshot so an old in-flight pull cannot admit actions after an edit. Action-only edits reset only the affected rule's transition/cooldown state. Epoch changes reset camera transition baselines and preserve cooldown, as in phase 2. Jobs contain immutable action snapshots and monotonically assigned rule/camera revisions. Eligibility is checked before each attempt and immediately before sending: edits, removal, disable or identifiable self-targets invalidate queued work. Already initiated HTTP cannot be recalled. Recreating a rule does not reuse its previous revision.

The worker captures one startup camera snapshot; it does not supervise or reconcile multiple workers. It stops forwarding when that snapshot becomes obsolete. Starting/replacing workers after configuration changes remains phase 4. Discovery, unfiltered subscription, sequential pulls, lease-relative renewal and bounded best-effort unsubscribe reuse the pinned 0.11.2 API and adapter. Convenience calls are bounded with WaitAsync and client disposal; abandoned faults are observed. Shutdown aborts the polling transport and uses a fresh client for a maximum three-second unsubscribe. Reconnect has capped exponential backoff and jitter. Worker status contains fixed labels only.

## Bounds and delivery semantics

- Queue: 100 pending globally, 25 pending per rule, four active globally and one active per rule. The per-rule admission refinement is recorded in REQUIREMENTS R4 and the phase 3 plan: a single burst must leave space for other rules. Admission is synchronous and never waits for network work. Overflow rejects the new job, increments a locked counter and records a safe status. FIFO within each rule and round-robin across eligible rules prevent a backlog from dominating execution. Active retries retain that rule's slot; other slots remain independent.
- Cooldown remains monotonic, atomic and per rule across identities, starting only on successful queue admission. Delivery failures, expiration and cancellation after acceptance consume it. Overflow consumes no cooldown. Suppressed/rejected events are never replayed. Manual tests bypass matching, transition state and cooldown, share all queue/transport limits and support cancellation. They require an enabled configured camera but may explicitly test a disabled rule; they do not enable it.
- Attempts: ten seconds each; 30 seconds total from admission, including queue age and delays; zero additional attempts by default, explicitly up to two. Retry only transport/attempt-timeout failures, 408, 429 and 5xx. Short delays have jitter unless Retry-After supplies a delay/date. A retry whose delay cannot fit the remaining deadline ends safely without sending early. Ordinary 4xx and redirects do not retry. Retries may duplicate effects, including action-like GET requests; no exactly-once or durable replay guarantee exists.
- Requests: HTTP/HTTPS GET or POST only; URL at most 8192 UTF-16 units; no embedded credentials, fragments or control characters. At most 32 headers, 16 KiB combined UTF-8 header names/values; names and typed header values are validated, duplicates are rejected, transport/content-controlled headers and control characters are forbidden. Headers are copied and applied to each new request. Optional POST body is literal valid JSON, at most 64 KiB UTF-8 and depth 64; GET bodies are rejected. Configuration has at most 256 rules, retaining phase 2 matching-string bounds. Camera credentials are capped at 4096 units each.
- Transport: redirects, proxy use and cookie sharing are disabled; normal TLS certificate validation remains. Connection-time DNS resolution rejects link-local, multicast, unspecified and known metadata destinations, including mapped addresses. Private destinations remain permitted. The socket connects to the checked addresses without a second DNS lookup. Known application origins are rejected before execution; this is not a universal DNS-alias/self-host identification guarantee. Local recorder traffic is explicitly permitted by the test scope.
- Response headers are capped at 32 KiB; responses use ResponseHeadersRead and are disposed without reading/storing bodies. Status snapshots retain time, result category, job/rule ID, attempts, HTTP code and duration. Latest-admission status and latest-finished execution are separate, so overflow/new admissions cannot erase the last finished result. Both maps are bounded by configured rule count and removed with rules. HttpClientFactory request loggers are removed. Optional delivery logs contain only generated job IDs, fixed result categories, attempt/status numbers and duration; no URLs, header values, bodies or exception text. Application logging providers remain cleared by the shell.
- ONVIF: request at most 100 messages per pull; the version-matched protected settings impose a 1 MiB buffered SOAP response limit on generated discovery/subscription/pull clients and renewal/cleanup. All notifications exposed by a bounded response are inspected, even if a nonconforming sender exceeds the requested count. Existing per-event 64 KiB/string/count limits and 100-event/1 MiB history bounds remain. Unsupported subscription reference parameters fail closed; general reference-parameter interoperability is still unverified.
