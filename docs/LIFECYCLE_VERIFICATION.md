# Phase 4 lifecycle verification and handoff

Date: 2026-10-15. Generic phase 4 implementation and required automated gates are complete. Only disposable onvifsim instances, synthetic credentials and local HTTP recorders are used. Physical-device activation/reset mappings and real-device outage/recovery remain **pending**. HTTP 2xx proves transport acceptance only.

## Delivered scope

`CameraSupervisor` replaces the single startup worker with one independent sequential `CameraSubscriptionWorker` task/client/subscription per enabled camera. `CameraPipeline` is the renamed and extended phase 3 `SingleCameraPipeline`; its normalizer, RuleState, inspector, queue, dispatcher, execution status and shared WS-Addressing adapter are reused. `AddCameraPipeline()` registers these concrete services. Call `CameraPipeline.ConfigureCameras(cameras, actionRules)` for an atomic in-memory replacement before or during host execution. `Configure(camera, actionRules)` remains a one-camera convenience method. The default executable has no configured cameras/actions and exposes only health. No configuration loader, administration/authentication APIs, persistence, UI, Compose, workflows or TaskFlow was added.

The configuration resource bound is 64 cameras and the existing 256 rules globally. A capacity-one notification channel coalesces configuration changes; the supervisor always rereads the newest snapshot. Unchanged cameras retain their snapshot identities and revisions. Any camera edit (conservatively including its name), disable or deletion invalidates its queued jobs immediately. Old pull results still enter inspector history but cannot update rule state or admit work. Removing/recreating equal configuration cannot revive old pulls or jobs. Rule and action revision checks before HTTP attempts remain unchanged; editing one camera does not invalidate another's jobs.

Reconciliation cancels all obsolete workers, joins their cleanup, disposes their cancellation sources, then starts replacements from the latest configuration. No replacement for a camera starts while its obsolete task is running. Unchanged cameras and the dispatcher continue independently during cleanup/backoff. Deletion removes status; disabling retains safe contact/event timestamps and reports Disabled after cleanup. The single-camera-only snapshot/global-epoch accessors were removed; subscription epoch reset now requires the current camera snapshot. The supervisor's internal delegate seam exists only to test cancellation/cleanup ordering without network work.

## Timing, status and failure boundaries

Each attempt creates a fresh bounded client, rediscovers services and subscribes without filters. Successful subscriptions reset only that camera's transition baselines, preserving cooldown. Epoch is a per-worker successful-subscription counter; a configuration replacement starts a new worker counter. LastContact advances on successful discovery, subscribe, renewal and pulls, including empty polls. LastEvent advances only when a notification is received. Status contains camera ID, fixed state, timestamps, epoch and a capped failure counter. States are Disabled, Connecting, Subscribed, Reconnecting, Error and Stopped. Error after three consecutive unsuccessful attempts remains recoverable; it does not stop retries or other cameras.

Requested lease is 120 seconds. Returned CurrentTime/TerminationTime define a monotonic lease budget, conservatively charged from request start. Expired/unusable timing, invalid-subscription faults, renewal refusal, authentication/service faults and transport errors trigger bounded cleanup and resubscription with fresh discovery. Renew at 30 seconds remaining; renewal is bounded by ten seconds and the remaining lease. Poll for at most 20 seconds, reserving 20 seconds from the lease when selecting long-poll duration, with a request deadline at most poll duration plus ten seconds and never beyond the remaining lease. Unusable short renewed leases are recreated. All operations remain sequential within a camera. Empty polls are successful contacts; responses completing immediately are paced by 250 milliseconds.

Reconnect delays grow exponentially from 0.75–1 second to a 22.5–30 second cap, with fresh jitter. A subscription that repeatedly fails immediately does not reset backoff merely by being created; 30 seconds of successful session contact resets the failure counter. Unit tests check timing decisions and jitter bounds without wall-clock delays.

Cancellation disposes the polling transport and cancels renewal. The pinned convenience calls have no cancellation parameter, so WaitAsync bounds them and abandoned faults are observed. A fresh cleanup transport attempts unsubscribe for at most three seconds, then is disposed. Cleanup runs concurrently across stopped cameras; the documented worker/supervisor stop target is five seconds, including scheduling allowance. Tests enforce this ceiling during an outstanding poll and delayed unsubscribe; host callers must allow that budget. After successful discovery on recovery, the worker retries its last failed cleanup address once with a cancellable three-second deadline before subscribing again. Only one pending cleanup address is retained per worker. Cleanup is best effort: a remote server may retain an unreachable subscription until its lease expires, especially after deletion, configuration replacement or shutdown. Unsupported endpoint-reference parameters still fail closed; general reference-parameter interoperability is not claimed. SOAP response, event/history, dispatch, HTTP deadline and retry bounds remain those recorded in the phase 3 handoff.

## Repeatable automated verification

Prerequisites: .NET 10 SDK, PowerShell 7, Linux Docker engine and `./tests/Build-OnvifSimulator.ps1`. Simulator is still source version 0.1.0 at pinned commit `8f86706c2ba768006e85b38f6bc1c760d36f1bba`; no dependency versions changed. The local source and restored 0.11.2 client source/sample already reviewed in earlier phases were inspected before reusing subscription, renewal and cancellation calls.

Final commands and outcomes (.NET SDK 10.0.402, net10.0/C# 14, SharpOnvifClient/Common 0.11.2):

- `dotnet clean OnvifWebhookBridge.slnx -v quiet`, followed by `dotnet build OnvifWebhookBridge.slnx --no-restore --disable-build-servers -m:1 -v minimal`: passed, zero warnings/errors. The final incremental build before the full suite also passed with zero warnings/errors.
- `dotnet test OnvifWebhookBridge.slnx --no-build --no-restore -v minimal`: **66 passed, 0 failed, 0 skipped** (64 unit cases and two onvifsim integration cases), final suite duration about 1 minute 44 seconds.
- `./tests/OnvifProbe.Smoke.ps1`: passed the preserved six-event synthetic console, repeat/false, duplicate/extension/raw content, addressing and fault-resubscription assertions. The harness terminates its child; Ctrl+C is not verified by this harness.
- `./tests/Verify-Phase4Native.ps1`: final Linux x64 publish and actual native runtime scenarios passed, with no AOT/trimming warnings or added suppressions. The old Phase2 script delegates to this runner.

Four new deterministic unit cases cover lease/backoff bounds, independent camera revisions and removal/recreation, stale-pull inspector admission, atomic invalid configuration rejection, cleanup-before-replacement with coalesced rapid edits, one active worker per camera and joined shutdown, and per-camera epoch reset with preserved cooldown. Existing unit/probe/addressing regressions are retained; tests referencing the old pipeline/registration names were updated to the renamed API. The old simulator forwarding scenario now uses the supervisor with one camera; its assertions were preserved. No tests were removed, skipped or weakened to conceal failures.

The new shared `LifecyclePath` runs against two generic cameras in an actual onvifsim container, each with independent HTTP and RTSP ports. It uses `/api/scenario`, `/api/cameras/{id}/events`, PATCH fault switches, `/offline?seconds=3` and `/sessions`. Event delivery is verified by a local Kestrel recorder while one camera fails; the healthy camera retains its epoch and continues delivery. It verifies two empty long polls, renewal without a new epoch, invalid subscription, actual expiration of an existing lease, renewal refusal, immediately expired new leases, unsupported GetServices, wrong synthetic credentials, offline/restart recovery, connection/name edits with observations from the replacement, disable/enable/delete and bounded delayed unsubscribe. Native/JIT scenarios verify transition re-baselining after reconnect and subsequent false-to-true delivery. Final session and HTTP-client counts must both reach zero. Lease shortening and invalidation use the real ONVIF Renew/Unsubscribe operations against the simulator, not fabricated SOAP responses or a fake transport.

The native runner executes the preserved normalization/subscription/HTTP scenarios and this same lifecycle scenario. Its explicit source allowlist is staged into a unique ignored `.local/` directory and built as a test-only image; no private configuration/cache/captures enter the context. SDK/runtime-deps Noble digest pins are unchanged; clang 18, Linux x64, actual native executable under the non-root runtime account. This is local Linux/amd64 container execution, not arm64, emulated execution, deployment-host or physical-device evidence. No AOT/trimming suppressions were added.

Development failures are not passes: the first two-camera scenario inherited a conflicting default RTSP port; unique synthetic RTSP ports corrected it. A later endpoint-edit test used a query URL unsupported by onvifsim; the corrected fixture uses another service route registered by the simulator's actual SOAP dispatcher and verifies a new subscription address and an observation carrying the edited name. The initial native publish succeeded but its runtime gate failed before these fixture corrections. A subsequent outage assertion found a retained remote subscription after the peer was unavailable throughout cleanup. This was a production lifecycle gap: recovery now retries the last failed cleanup address before resubscribing, and the scenario explicitly requires exactly one remote subscription after recovery. The assertion was retained and strengthened. The final green JIT and native runs above supersede these failed development attempts; required coverage was not skipped or suppressed.

## Scope/secrets audit and pending checks

Before any Docker mutation, container/image/builder inventory found no leftover bridge test/build containers and found a completed phase3-local image. That image and unrelated resources were preserved. Only disposable fixture containers/test images were created; fixture containers are removed automatically. No deployment was performed, and no images or commits were pushed/published.

The scoped diff contains only generic production/test sources and planning/evidence updates. Synthetic credentials, reserved example domains and runtime-generated local fixture addresses are intentional. The new lifecycle/status code logs no URLs, arbitrary exception text, credentials, headers, JSON or SOAP. HttpClientFactory loggers remain removed, the application's logging providers remain cleared, and the original seeded-secret redaction regression remains part of the full suite. Private `.local` configuration, caches and staging stay ignored. The diagnostic console and shared renewal adapter were not changed.

**Hardware/platform gates pending:** privately validate at least two activation/reset cycles per real transition mapping, Source/Data selector/value, stable Source/Key identity and property operation; use occurrence mode where reset is absent. Real-device reboot/network outage and recovery, real destination action semantics, Linux arm64/native hardware and deployment-host verification remain unverified. No real camera, destination or device settings were contacted/changed in this phase. Phase 5 and later implementation requires new authorization.
