Concrete findings and fixes:

- The health command had a time limit but buffered an unlimited response. It now accepts exactly the seven UTF-8 bytes of `Healthy`, with a seven-byte buffering limit and the existing four-second total deadline. A shared JIT/NativeAOT regression exercises a valid chunked response, an oversized response whose sender never finishes, a stalled response, a redirect that must not be followed, and a non-200 response. Oversized input must fail before the total deadline. The existing storage-failure/port regression remains intact.
- The ten-minute deployment loop generated events and checked health without asserting continued delivery. It now triggers each camera separately and requires recorder progress and a new successful job for that camera's rule on every cycle, checks both subscriptions, and records the completed cycle count. Rule-specific results prevent one camera's delayed/reset traffic from masking the other's failure. Invalid/nonpositive soak durations are rejected. Earlier ten-minute results remain historical traffic/health evidence; the strengthened assertions have separate results below.
- Compose reset reused the bootstrap password and only checked health. It now checks initial login, changes the password file offline, rejects the old password after reset/recreation and accepts the replacement. The fixture also explicitly selects the shipped Compose file (avoiding implicit overrides or inherited `COMPOSE_FILE`), forces loopback, ignores operator `.env` settings and restores inherited variables instead of deleting them.
- Release runs for the same version could overlap and overwrite shared platform tags before manifest assembly. Workflow-level concurrency now serializes the entire release for each tag with `cancel-in-progress: false`; an active publisher is allowed to finish. This uses [GitHub's documented concurrency contract](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency). Configuration is linted locally; actual hosted scheduling/publication remains pending. Operators must restrict release-tag updates/deletion as well as creation.

No existing regression was removed, skipped or weakened. Application production changes are confined to the phase 8 health command; release scheduling is the only workflow change. Docker/base/dependency pins, supported platforms, authenticated endpoints, persistence/schema, matching/dispatch, supervisor cleanup and renewal contracts are unchanged. Review found no additional justified application changes in Compose or HTTPS configuration; hosted execution remains pending rather than inferred from local lint.

## Production deployment scenarios and resource observations

The deployment runner starts two actual onvifsim cameras with independently discovered event/subscription endpoints on a disposable bridge network, plus a local recorder. It authenticates to the real production APIs, configures cameras and POST rules and verifies actual event delivery across the bridge. It checks the packaged browser shell, UID 1654, mounted directory 0700 and DB 0600, custom internal port, health command and continued health while the simulator is stopped. SIGTERM must exit zero within the 15-second allowance. Container removal/recreation retains masked secrets and configuration on the named volume; the final script also requires restored subscriptions and resumed delivery.

TLS acceptance is tested separately from transport HTTP: a disabled synthetic HTTPS action must fail with an untrusted recorder certificate. After recreation, the recorder's public synthetic CA is supplied through writable tmpfs and system trust configuration; the same stored action must return 204 with ordinary validation. No certificate callback/bypass is used. The test certificate/key exists only in the disposable recorder; only its public CA is copied to ignored local staging. The separate inbound TLS smoke generates a synthetic server key/certificate in memory, streams its temporary PFX into the disposable container and verifies standard Kestrel HTTPS configuration from a certificate-validating host client. Only public trust certificates remain in ignored staging. Actual deployment-host CA/proxy interoperability and native ARM64 cold-handshake performance remain pending.

Sparse local observations (not benchmarks or guarantees): production image sizes are 210,744,720 bytes amd64 and 233,467,753 bytes arm64. Startup-to-first-health was about 1.06 seconds amd64 and 10.30 seconds under ARM64 emulation. Early idle samples were 15.5 MiB/0.01% CPU amd64 and 66.26 MiB/58.34% CPU under emulation, including startup work. The final ten-minute loaded samples were 47.75 MiB/0.04% CPU amd64 and 119.2 MiB/0.03% CPU ARM64 emulation. The final repeat started in 1.96 seconds amd64 and 16.82 seconds under emulation; post-recreation first health took 0.95 and 2.52 seconds respectively. Concurrent fixtures and emulation materially affect these samples. Both ten-minute scenarios and their recreation/TLS checks completed with exit zero; no physical-host capacity claim is made.
