# TaskFlow dispatch migration

Scope: explicitly authorized 2026-10-25. No physical camera, real destination, deployment, release publication or image publication is involved. Recorder 2xx responses establish transport acceptance only.

## Dependency and ownership

Production references the published NuGet package [TaskFlow 1.1.0-rc.9](https://www.nuget.org/packages/TaskFlow/1.1.0-rc.9), without extension packages, copied library source or project references. The restored nuspec identifies source commit `36a1b62d590fb70ef7ee702e2f45fa9165f22719`. Reviewed the matching [admission documentation](https://github.com/dombrovsky/TaskFlow/blob/36a1b62d590fb70ef7ee702e2f45fa9165f22719/docs/extensions/admission.md), [keyed scheduling documentation](https://github.com/dombrovsky/TaskFlow/blob/36a1b62d590fb70ef7ee702e2f45fa9165f22719/docs/extensions/keyed-scheduling.md), coordinator, submission, completion middleware and lifetime sources. The package has a dependency-free .NET 10 target.

`HttpActionDispatcher` is one DI singleton, also registered as the hosted service. It owns one original `TaskFlow` and its immutable keyed scheduler branch: ordinal string rule keys, concurrency four, global pending capacity 100 and per-key pending capacity 25. `TrySubmit` makes the synchronous combined admission decision. There is no application scheduler lock, worker loop, channel, pending-job collection, active-key set, admission waiter or observer registry. `DispatchQueue`, `TakeAsync`, `Complete`, queue rotation and semaphore signalling are removed. The dispatcher retains the existing HTTP implementation; passing the pipeline with each immutable submission avoids a DI cycle.

Completion middleware publishes cancellation or a fixed transport-failure status when execution never reaches the HTTP delegate. Rejected submissions are ignored there and remain observable through pipeline overflow status and the dispatcher's `Rejected` counter. Accepted completion tasks have a non-throwing task-only observation callback; middleware owns all status publication before the original flow's lifetime finishes. No asynchronous observer task or `async void` callback is created. The second simplification pass removed a provisional observer counter and drain mechanism in favor of this library-owned completion path.

Hosted stop disposes the original flow asynchronously: admission closes, queued work is cancelled without HTTP invocation, active requests/retry delays receive cancellation, and shutdown waits for underlying delivery and completion middleware. Async DI disposal and synchronous disposal use the same original flow; repeated disposal is supported by TaskFlow. Stop waits for settlement even if the host's stop token expires, keeping the HTTP factory and pipeline alive until work settles. Existing application deadlines bound cooperative HTTP execution. A custom transport that ignores cancellation can still delay shutdown, as cooperative cancellation cannot forcibly terminate it.

## Preserved contracts and timing differences

`CameraPipeline.Process`, `ManualTest` and `RuleState.Process` remain synchronous. Configuration, immutable job snapshots, matching and admission retain the existing lock order. History precedes matching; successful admission alone consumes cooldown. Transition evaluation, stale-revision checks, HTTP deadline/timeout/retry/Retry-After behavior, response limits, TLS isolation, address/DNS restrictions, redirect blocking and secret-safe diagnostics are retained. No TaskFlow timeout/retry/throttle/enqueue interception is configured.

`Queued` is published before `TrySubmit` under the existing pipeline lock. Execution/status publication cannot overwrite it and then suffer a late queued write. `Record` retains its job-ID check, so an older completion cannot replace a newer admission's per-rule status. `LastExecutions` continues to mean the last completed execution per rule, which may differ from the latest admission. A normally entered HTTP delegate publishes its terminal result itself; completion middleware only handles failed scheduler outcomes, avoiding duplicate terminal records.

TaskFlow pending capacity includes already-dispatched work until the user delegate actually starts. The old queue removed it when a consumer claimed it. A paused scheduler test verifies all 100 pending slots and each 25-slot per-rule quota remain occupied before actual execution; four active delegates subsequently do not consume pending capacity. Brief scheduling delay can cause an earlier rejection than the former implementation. No compatibility queue is introduced.

Already-cancelled manual tests retain accepted-then-cancelled behavior, with no HTTP request. A cancellation racing the reservation can win TaskFlow admission: the pipeline returns false with `Cancelled`, without overflow or cooldown consumption. It does not resubmit that operation, because TaskFlow may already own its cancellation completion. Accepted manual cancellations and shutdown cancellations remain terminal even when their delegates never start.

Configuration-only validation instances pass no dispatcher; they validate snapshots without allocating a scheduler or creating outbound work. Production DI always supplies the singleton dispatcher. Scheduling coverage moved out of direct queue inspection into actual TaskFlow/HTTP tests. Equivalent-save/recreation/camera-revision checks now exercise delivered or stale results. Shared TLS checks hold a real request open, edit TLS while the next operation is queued and verify it becomes stale. The shared ONVIF path holds four real recorder requests, fills 100 pending jobs, observes three real-event rejections with inspector history intact, then drains and verifies forwarding.

Test synchronization uses paused actual TaskFlow execution, HTTP gates, completion-log signals and fake-clock timer registration.

- Changed-file Gitleaks scan passed with zero findings; scope/privacy and diff-whitespace review passed. All generated source downloads, images/staging evidence and logs remain local/ignored. No image, release, deployment or physical-device action was published.

Production diff against the starting `main`: **102 lines added, 155 removed (net 53 removed)** across application C# and its project file. C# alone is 101 added / 155 removed. `DispatchQueue` accounts for 115 deleted lines; the HTTP retry/security implementation remains in place. Added code handles TaskFlow configuration, explicit completion/status mapping and the initial-status/admission-cancellation races. The simplification removes scheduling algorithms and their mutable collections instead of reimplementing them behind another interface.

Development checks corrected the old harness's assumption that HTTP delivery and retry-timer creation occurred on the submitting stack. Tests now wait for actual timer registration. A review also removed cancellation resubmission: pre-admission cancellation may already have a TaskFlow completion, so submitting again could duplicate the same job. Windows build-file contention from overlapping JIT builds was resolved by serializing subsequent solution builds. A malformed shell log redirection was corrected; only the recorded successful reruns are counted. No failing behavior test was skipped or relaxed.

Hardware gates remain pending: real activation/reset cycles and stable transition identities, reboot/outage recovery and real destination side effects. Local simulator and emulated execution cannot establish these properties. Linux ARMv7 and Linux 32-bit x86 are not newly supported.
